# CI kinds

The forge-neutral catalogue of the CI kinds pipelith knows. A kind here
says what a pipeline is for, when it runs, which secrets it needs and
which row values it takes. How a forge spells that is the forge crate's
page: `docs/KINDS-GITHUB.md` in actlith, `docs/KINDS-GITLAB.md` in
lablith.

A kind enters this catalogue only when it renders on both forges
(SPEC.md V5). A row that validates against it renders on both, so moving
a project from one forge to the other changes the config file name, not
the rows (SPEC.md V4). This page and `src/kind` must agree (SPEC.md
V11).

Shapes come from actlith at commit `7ce69c6`, whose catalogue came from
the fleet survey of 2026-10-15.

## Common to every kind

- Every generated file starts with the header from `src/files`:
  `# generated by <tool> gen from <config>; do not edit`.
- Least privilege: the pipeline reads the repository; a job that pushes
  or opens a change request widens only what it needs.
- One run per ref at a time: push and change-request runs cancel an
  older run of the same ref; scheduled runs are never cancelled, since a
  cancelled bump can leave a half-pushed branch.
- Every job has a timeout (row arg `timeout`, minutes, default 30,
  1 to 360).
- Every job installs nix and trusts the row's cache; the cache push is
  skipped when the run comes from a fork, which gets no secrets.
- Every command is one line. Logic longer than one command lives in a
  script the forge crate seeds into the repository, so shellcheck, bats
  and xenolith see it.

## Row values

Section `## workflows`, columns `id|kind|systems|cache|args`, the same on
both forges.

- `id`: the pipeline's name and file stem; unique in the section.
- `kind`: one of the kinds below, or a forge-only kind the forge crate
  declares (reported by the portability check).
- `systems`: nix systems, comma-separated; `-` takes the kind's default.
  `x86_64-darwin` is refused: no forge hosts a runner for it.
- `cache`: a cachix cache whose public key pipelith knows (v1:
  `pr0d1r2`); `-` means no cache steps.
- `args`: `key=value` pairs, comma-separated, checked against the kind's
  schema; an unknown or repeated key is an error, never ignored. A
  forge-only key is accepted only by the forge that declares it.

## Secrets, by purpose

- Cache push: the cachix auth token. Read-only cache use needs none.
- Open a change request: a token allowed to push a branch and open a
  pull request (GitHub) or merge request (GitLab). Row arg `token` names
  it; its default is the forge's built-in job token.

## `gate`

The hk gate on every supported system.

- Events: push to the default branch, change requests, manual runs.
- One job `gate` per system; its name is stable, since branch
  protection reads it.
- Steps: full-history checkout (the semver step needs tags), nix, cache,
  then the gate command.
- Default systems: `x86_64-linux`, `aarch64-linux`, `aarch64-darwin`.
- args: `command` (default `nix develop --command hk check --all
  --check`), `timeout`.

## `build`

Build and cache a flake package on every system, then prove the cache
has it. For packaging repositories.

- Events: as `gate`.
- Job `build`: per system, build `.#packages.<system>.<package>`; cache
  push only from the default branch.
- Job `check`: `nix flake check --all-systems`, then evaluation only for
  systems without a runner (`x86_64-darwin`), so they cannot rot.
- Job `verify-cache` (after `build`, default branch only): every
  system's output path answers from the cache, since a failed cache push
  does not fail its job.
- args: `package` (required), `timeout`.

## `update-pins`

Follow `nixpkgs-lock` and propose the bump as a change request. Pull
model: the consumer polls; nixpkgs-lock holds no cross-repository token.

- Events: a schedule (cron from args), manual runs.
- Needs: push a branch, open a change request.
- Steps: checkout that keeps credentials, nix, the seeded update script:
  update the input, build, push branch `pins/nixpkgs-<short rev>`, open
  the change request; idempotent when the branch exists.
- args: `cron` (default `50 6 * * *`, after nixpkgs-lock refreshes),
  `build` (flake attribute built before proposing; default
  `.#default`), `token` (forge default), `timeout`.

## `upstream`

Poll an upstream release and propose the bump as a change request. Same
pull model and change-request mechanics as `update-pins`.

- Events: a schedule (cron from args), manual runs.
- Steps: checkout, nix, read-only cache, the repository's own bump
  script (path from args; it reports the new version), then the seeded
  open-change script.
- args: `script` (required), `cron` (default `20 6 * * *`),
  `branch-prefix` (default `upstream/`), `token` (forge default),
  `timeout`.

## Not in the catalogue

One-off pipelines stay hand-written and are declared by each forge
crate's own section (actlith `## hand-written`). A kind is added only
when two fleet repositories need it and it renders on both forges.
