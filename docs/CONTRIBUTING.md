# Contributing to pipelith

Thanks for looking. The working rules live in [`AGENTS.md`](../AGENTS.md),
written for humans and coding agents alike; this page is the short
version.

## Getting set up

Enter the dev shell with `direnv allow` or `nix develop`. Every tool the
gate runs comes from it, pinned by `flake.lock`, and the shell points git
at the tracked hooks in `.githooks/`.

## The gate

Every commit runs hk's pre-commit and commit-msg hooks; every push runs
the full gate, which you can also run by hand with `hk check --all`. The
hooks refuse when hk is missing. Never use `--no-verify`: when the gate
refuses, it is working, and its message says what to do.

## Commits

- One change per commit, and the failing test before the code.
- Subject `type(scope): claim`, at most 72 characters; the body says why.
- A `feat`, `fix` or `perf` commit that changes `src/` adds a line under
  `## [Unreleased]` in [`CHANGELOG.md`](../CHANGELOG.md).
- A change to the bytes the YAML writer or the generated header emits is
  at least a minor version, and its changelog entry names the change:
  every consumer's generated files change with it.
- A new gate step comes with proof, in its commit body, that it rejects a
  planted violation.

## Design

The design is a federated spec: [`SPEC.md`](../SPEC.md) at the root and one
`SPEC.md` per node under `src/`, `tests/`, `dev/` and `nix/`. Change the
spec with the code it describes. The `NAV` tables are generated by
`sherd sync`; never edit them by hand.

Two rules decide most reviews. Nothing forge-specific lands here: no
pipeline keys, runner labels, action pins or expression syntax of any
forge (the `forge-neutral` step greps for them). And a kind enters the
catalogue only when it renders on every forge pipelith serves; a kind
one forge needs alone belongs in that forge's crate.

## Reporting problems

Bugs and ideas go in GitHub issues. Security problems go through
[`SECURITY.md`](SECURITY.md), not a public issue.
